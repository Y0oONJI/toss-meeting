# 토스 과제 - 6명이 회의 일정을 잡는 경험 설계

---

## Q1. 사용자의 어떤 문제를 발견했나요? 그것이 왜 문제라고 생각했나요?

### 실제 플로우 분석

1. **[Pain 1]** 조율자가 가능한 시간을 질문한다
   - 시간을 정하는 것 자체가 어려움. 팀 내 관례가 있으면 그 시간대를 쓰거나, 아니면 막연하게 던지는 상황

2. **[Pain 2]** 참여자들이 질문을 확인한다
   - 늦게 확인하거나, 답하기 불편해서 피하거나, 잊어버리는 경우 발생

3. **[Pain 3]** 참여자들이 가능한 시간을 답한다
   - 형식이 제각각 (A는 "일요일 12시", B는 "토요일"처럼) → 추가 질문이나 해석 필요

4. **[Pain 4 - 핵심]** 조율자가 교집합을 찾는다
   - 일정을 하나하나 수동으로 비교
   - 안 되면 다시 물어보고, 또 안 되면 또 조율 → **루프 반복**
   - 심한 경우 기존 일정 우선순위까지 재조율 필요

5. **[Pain 5]** 최종 확정 및 공유
   - 모두에게 동일하게 전달, 장소 안내, 리마인드 필요

6. **[Pain 6]** 각자 캘린더에 등록

---

### 문제 정의

> **조율자 관점**
> 회의 일정 조율자는 참여자 6명의 가능한 시간을 각자 수집하고, 교집합을 직접 찾고, 안 맞으면 다시 물어보는 과정을 반복해야 하기 때문에 일정 조율에 과도한 시간과 에너지가 든다.

> **참여자 관점**
> 참여자는 본인 일정을 직접 파악해서 답해야 하는 부담이 있고, 조율자에게 직접 "안 된다"고 말해야 하는 심리적 불편함이 존재한다.

## Q2. 그 문제를 어떻게 해결했나요?

### 솔루션 요약

내 솔루션은 조율자와 참여자 둘 다 의견을 쉽게 조율할 수 있도록 사용자의 유형(롤)을 구분하고, 서로 같은 형식으로 정보를 입력하여 시스템이 계산할 수 있도록 해준다. 그리고 결과적으로 조율이 안 된다면 시스템이 조율자에게 대안을 제시한다.

### 역할 정의

| 역할 | 설명 |
|------|------|
| 조율자 | 회의를 소집하고 참여자를 초대, 최종 확정. 어드민 역할 |
| 꼭 참석 | 참여자가 본인이 직접 선택. 교집합 계산의 기준 |
| 가능하면 참석 | 참여자가 본인이 직접 선택. 꼭 참석 교집합 안에서 최적화 |

> 참여자에게는 조율자 외 다른 참여자가 익명으로 보임

---

### 조율자 플로우

1. 회의 생성 (제목, 기간 설정) → 초대 코드/링크 생성
2. 참여자에게 링크 공유
3. 모아진 시간대 확인 (익명으로 표시)
4. 시스템이 교집합 자동 계산
   - 교집합 있음 → 조율자 컨펌 → 최종 확정
   - 교집합 없음 → 시스템이 조율 필요한 참여자 파악 → 조율자가 해당 참여자에게 시간대 제안 발송 (강제 없는 UX)
5. 참여자 응답 후 재계산
   - 2회 이상 조율 실패 시 → 시스템이 다수결 결과 제시 → 조율자 최종 확정
6. 확정된 시간 전체 참여자에게 공유

### 참여자 플로우

1. 초대 링크/코드로 입장
2. 이름, 직급/직군 입력 + 참석 유형 선택 (꼭 참석 / 가능하면 참석)
3. 가능한 시간대 입력 (같은 형식으로)
4. 다른 참여자들이 제안한 시간대를 익명으로 확인
5. (조율 필요 시) 시스템에서 알림 수신 → 2개 시간대 제안 받기 + 직접 입력도 가능
6. 최종 확정된 시간 확인

### MVP 범위 밖

- 캘린더 연동
- 참석 불가 옵션
- 로그인/회원가입
- 시간대 추천 기능 (로그인/히스토리 데이터 없이는 추천 기준이 불명확해서 오히려 노이즈)

## Q3. 왜 이 방식으로 설계했나요?

**같은 형식으로 입력하게 한 이유는,** 날짜를 고르는 과정에서 모든 사람의 답변 형식이 달라 재확인이 필요할 수 있고, 구두로 답변할 경우 명확성을 확인하기 위해 조율자가 한 번 더 확인해야 하기 때문이다.

**시스템에 직접 입력하게 한 이유는,** 참여자가 조율자에게 직접 의사를 전달하는 것이 아니라 시스템을 통해 입력하기 때문에 조율자에게 직접 말해야 하는 부담 없이 본인 일정을 솔직하게 제출할 수 있기 때문이다.

**필수/선택 참여자를 구분한 이유는,** 조율 과정에서 필수 참여자의 일정이 우선순위가 될 수 있도록 시스템이 판단하기 용이하게 하기 위함이다.

**교집합이 없을 때 시스템이 대안을 조율자에게만 제시하는 방식을 선택한 이유는,** 조율자가 모든 경우의 수를 직접 계산하는 부담을 줄이고, 대안이 전체 참여자에게 공개될 경우 특정 참여자가 지목당하는 느낌을 받을 수 있기 때문이다.

---

## 메모 (정리 중인 생각들)

- 필수/선택 구분은 조율자가 지정 → 회의 맥락을 가장 잘 아는 사람이 결정
- 참여자가 시스템에 입력하면 조율자에게 직접 "안 된다"고 말하지 않아도 됨 → 심리적 부담 감소
- 대안 제시를 조율자에게만 보여주는 방식 → 지목당하는 느낌 없이 조율 가능
